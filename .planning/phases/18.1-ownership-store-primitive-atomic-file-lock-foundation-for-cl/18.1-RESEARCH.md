# Research: Phase 18.1: Ownership-store primitive

## Domain Research (File Locking in Node.js, exclusive-write, tmp-rename, PID checks)

Implementing concurrency primitives on a local filesystem without external dependencies requires strict reliance on system-level atomic guarantees provided by Node.js built-in `fs` and `path` modules.

### Atomic Acquisition (exclusive-create)
The fundamental primitive for checking existence and creating a file in a single atomic filesystem transaction is the `fs.openSync(path, 'wx')` system call:
- The `w` flag opens the file for writing.
- The `x` flag ensures exclusive creation. If the file already exists, the operating system rejects the operation and Node.js throws an error with `code === 'EEXIST'`.
- This operation is atomic at the OS kernel level, ensuring that two concurrent processes attempting to lock the same resource will never both succeed.

### Crash-Resilient Metadata Write (tmp-rename)
If a process crashes while writing JSON metadata into the lock file, the file may be left empty or corrupted (half-written JSON). A subsequent process reading this file would fail to parse it, causing lock check failures.

To solve this:
1. The process first acquires the filename space atomically using `fs.openSync(lockFilePath, 'wx')`. This guarantees no other process can claim it.
2. The file descriptor is closed immediately to prevent lockups (`fs.closeSync(fd)`), leaving an empty file.
3. The process writes its full JSON metadata to a unique temporary file path (e.g., `<lockFilePath>.<pid>.<timestamp>.tmp`).
4. The process calls `fs.renameSync(tmpPath, lockFilePath)` to replace the empty file with the complete metadata file.
   - On POSIX-compliant filesystems (including macOS and Linux), `rename` is guaranteed to be atomic.
   - The rename replaces the target file cleanly. Any concurrent reader will either see the empty file (before rename completes) or the fully populated file (after), but never a half-written intermediate state.

### Lazy Stale-Steal & PID Checking
If a process crashes or is killed abruptly, it will never release its lock. To prevent permanent deadlocks, the ownership store must support **lazy stale-steal** upon acquisition:
- If a lock file exists, the acquiring process reads and parses it.
- A lock is considered **stale** if:
  1. The JSON content is empty or corrupted (failed `JSON.parse` indicates a crash during write).
  2. The process ID (`pid`) recorded in the metadata is no longer active.
  3. The time since `acquired_at` exceeds `stale_lock_cap_seconds` (default 3600 seconds), protecting against infinite hangs in stuck/deadlocked processes.

#### Portable Process Health Verification
To check if the lock owner process is still running:
- Call `process.kill(pid, 0)`. Sending signal `0` does not terminate the process; it only performs permission and existence checks.
- If it returns without throwing, the process is alive.
- If it throws an error:
  - If `err.code === 'ESRCH'`, the process is dead (safe to steal).
  - If `err.code === 'EPERM'`, the process is active but owned by another user (not stale).
- If the `pid` field is missing or malformed, it is considered stale.

#### Race-Proof Stale-Stealing
If Process B and Process C both detect that Process A's lock is stale, they might race to overwrite it:
- If both processes write a new lock file and rename it, they might overwrite each other's lock, leading to both believing they own the lock concurrently.
- **Race-Proof Solution:** Before attempting to claim the stale lock, the process must atomically move the stale file to a unique trash path:
  `fs.renameSync(lockFilePath, lockFilePath + '.trash.' + process.pid + '.' + Date.now())`
- Only the process that succeeds in this rename operation gains the exclusive right to claim the lock. The losing process will receive an `ENOENT` error because the stale file was already renamed, and must retry the acquisition loop.

## Codebase Patterns (CommonJS module exports, error classes)

- **CommonJS Module Exports**: To align with all existing library files in `lib/`, `lib/ownership-store.js` must use `module.exports` and standard `require` imports.
- **Node.js Built-ins**: Strictly limit dependencies to standard modules (`fs`, `path`, `os`).
- **Error Conventions**: Rather than defining complex custom classes (which are not used elsewhere in the codebase), the store should throw standard `Error` and `TypeError` objects with descriptive messages and attach a custom `.code` property for clean programmatic filtering:
  - `LOCK_UNAVAILABLE`: Lock is held by a different, active process.
  - `LOCK_EXPIRED`: Lock has exceeded its TTL.
  - `OWNER_MISMATCH`: Release requested by someone other than the owner.
  - `INVALID_ARGUMENT`: Key or owner string is empty or invalid.

## Proposed Architecture (Design of lib/ownership-store.js API: acquire, release, list)

### The API of `lib/ownership-store.js`
The store will export a class `OwnershipStore` that manages locks inside a specific directory:

```javascript
const fs = require('fs');
const path = require('path');

class OwnershipStore {
  /**
   * @param {string} dirPath - Absolute path to the locks/claims directory.
   */
  constructor(dirPath) {
    this.dirPath = dirPath;
  }

  /**
   * Atomically acquires a lock.
   * @param {string} key - Lock identifier (filename slug).
   * @param {string} owner - Unique identifier for the owner (e.g. session ID).
   * @param {object} [options]
   * @param {number} [options.staleLockCapSeconds=3600] - Lock duration cap.
   * @param {string} [options.purpose] - Optional description.
   * @returns {boolean} True if successfully acquired.
   * @throws {Error} LOCK_UNAVAILABLE if held by another active process.
   */
  acquire(key, owner, options = {}) { ... }

  /**
   * Releases a lock if owned by the caller.
   * @param {string} key - Lock identifier.
   * @param {string} owner - Caller owner string.
   * @returns {boolean} True if released, false if the lock did not exist.
   * @throws {Error} OWNER_MISMATCH if owned by a different caller.
   */
  release(key, owner) { ... }

  /**
   * Lists all parsed locks, ignoring corrupted/half-written entries.
   * @returns {Array<object>} List of parsed lock records.
   */
  list() { ... }
}
```

### Idempotent Directory Creation in `lib/init-checks.js`
We will:
1. Add `.ai/claims` and `.ai/locks` to the required directories in `lib/init-checks.js`.

3. Make `bin/adp.js`'s `handleInit()` call `ensureDirsExist(repoRoot)` to ensure directory layout is correct.

### CLI/Doctor validation (`adp doctor`)
Extend `adp doctor` inside `bin/adp.js` to report current claims and locks:
- Instantiate `OwnershipStore` instances for `.ai/claims` and `.ai/locks`.
- Call `list()` on both to count active claims and locks.
- Output counts to stdout:
  `[doctor] Active claims: <count>`
  `[doctor] Active locks: <count>`

## Verification Strategy (Detailed test cases for race-proof acquire, stale steal, crash recovery, owner release check)

A new test file `validators/scripts/test-ownership-store.js` will verify the store's behaviors.

### Test Cases
1. **Greenfield Acquisition & Metadata Structure**:
   Verify acquiring a fresh lock creates a file containing a valid JSON payload matching the input options (`owner`, `pid`, `purpose`, `stale_lock_cap_seconds`, `acquired_at`).
2. **Double Acquire Blocks**:
   Verify that attempting to acquire an already active lock throws a `LOCK_UNAVAILABLE` error and does not overwrite metadata.
3. **Owner-Checked Release**:
   - Verify `release` succeeds when owners match (removes file).
   - Verify `release` throws `OWNER_MISMATCH` if requested by another owner.
   - Verify `release` on a non-existent lock returns `false` (no-op).
4. **Stale Steal - Dead PID**:
   Create a lock file with a non-existent PID (e.g. 999999). Verify `acquire` succeeds by lazily stealing the lock.
5. **Stale Steal - Time Cap Exceeded**:
   Create a lock file with a timestamp older than the stale lock cap. Verify `acquire` successfully steals the lock.
6. **Stale Steal - Malformed/Empty JSON**:
   Write a blank or corrupted text file to a lock path. Verify `acquire` successfully steals it.
7. **Race-Proof Stale-Steal**:
   Mock/simulate concurrent renames to assert that if Process B successfully moves a stale lock to `.trash`, Process C's attempt fails with `ENOENT`, preventing double ownership.
8. **Robust Directory Listing**:
   Write 2 valid locks and 1 empty/corrupt lock file. Verify `list()` returns exactly 2 records, ignoring the corrupted file.
