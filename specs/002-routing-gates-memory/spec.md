## Clarifications

### Session 2026-05-24

- Q: How should the pipeline status transition from `NEEDS_HUMAN_REVIEW` back to an active running state after human intervention? → A: Operator invokes the tool with a resume/override flag (e.g., `--resume` or `--override-gate`) which resets retry states.
- Q: How is the plain-text fallback for `Tool Unavailable` error mode presented? → A: Logged to a designated block report markdown file (e.g., `.ai/state/block-report.md`).
- Q: Where should the Human Review Packet be written? → A: Written to `.ai/reviews/<feature-slug>/human-review-packet.md`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Tool Routing & Gate Execution (Priority: P1)

As a pipeline operator or downstream agent, I want a structured tool routing matrix and clear gate statuses so that I can automatically determine which tool to run next and whether the active phase's gate criteria have been satisfied.

**Why this priority**: Establish the core control flow and gate boundary rules that orchestrate the pipeline from recon to shipping. Without this, agent execution remains an ad-hoc process rather than a structured protocol.

**Independent Test**: Can be verified by executing a simulated sequence of pipeline steps (Recon -> Critique -> Spec -> Spec Validation Gate) and confirming that the gate outputs explicitly format and parse the required status headers.

**Acceptance Scenarios**:

1. **Given** a new feature request, **When** the recon phase runs, **Then** it must output a structured recon session report specifying target files, and the gate must verify this output exists before proceeding.
2. **Given** a completed spec, plan, and tasks list, **When** the spec validation gate executes, **Then** it must scan for required headers and missing TODOs/clarification markers, writing `Status: PASS` or `Status: BLOCKED` with a parsed list of blocking issues.
3. **Given** a judgment-only gate review (e.g., critique or memory handoff), **When** non-blocking suggestions are made, **Then** the gate status may output `Status: WARN` with `Blocking Issues: none`, allowing execution to continue.

---

### User Story 2 - Run State Tracking & Verified Artifacts (Priority: P2)

As a pipeline validator, I want the mutable progress and verified artifacts to live in a dedicated state file rather than the narrow identity pointer, with verification evidence owned exclusively by gates.

**Why this priority**: Clean separation of concerns between feature identity (static feature path) and mutable pipeline execution details (retry counts, gate statuses, verifications).

**Independent Test**: Can be verified by querying `.ai/state/run-state.json` during execution and confirming that planning/execution agents cannot write to or mutate `verified_artifacts` directly, and that path drift check fails if specs live outside `specs/<feature-slug>/`.

**Acceptance Scenarios**:

1. **Given** an active feature setup, **When** the run starts, **Then** `.ai/state/active-feature.json` must only point to `specs/<feature-slug>/`, while all mutable counts/phases are logged in `.ai/state/run-state.json`.
2. **Given** an implementation plan generated by an agent, **When** the Spec Validation Gate passes, **Then** the gate updates `verified_artifacts` in `.ai/state/run-state.json` with the path, hash, and validator identifier.
3. **Given** a spec file or state file written to a legacy path (e.g., `.ai/specs/current/` or `.specify/specs/`), **When** path verification runs, **Then** it must fail and write a path drift blocking status.

---

### User Story 3 - Failure Taxonomy & Human Review Packets (Priority: P3)

As an execution agent or operator, I want standard failure modes, retry limits, and human review packets so that failures do not loop infinitely and human intervention is invoked with a clear context.

**Why this priority**: Prevents agent runaway loops and standardizes handoff back to the human operator when the system cannot proceed programmatically.

**Independent Test**: Can be verified by simulating three consecutive validation failures on a single gate and checking that the system halts, updates status to `NEEDS_HUMAN_REVIEW`, and writes a formatted human review packet.

**Acceptance Scenarios**:

1. **Given** an execution run that hits a compiler error, **When** the error is local, **Then** the agent stays in the execution step, applies a local fix, and does not mutate requirements or specs.
2. **Given** a required tool is missing, **When** the execution agent attempts to run it, **Then** it must gracefully degrade, write a block report to `.ai/state/block-report.md`, set status to `BLOCKED`, and output plain-text instructions.
3. **Given** three consecutive gate validation failures on `specs/<feature-slug>/spec.md`, **When** the fourth check runs, **Then** it must write a review packet to `.ai/reviews/<feature-slug>/human-review-packet.md` containing `blocking_question`, `recommended_answer`, `options_considered`, and `resume_instructions`.

---

### Edge Cases

- **Path Drift Collision**: What happens if a feature spec directory exists in `specs/<feature-slug>/` but a duplicate spec exists in `.ai/specs/current/`? The path check must flag this as a critical drift error and block all downstream stages.
- **Validation Loop Context Erasure**: What happens if the retry count is reset mid-loop? The retry counter must be bound to the specific phase and scope combination in `.ai/state/run-state.json`. Mutating other files must not clear this counter.
- **D-15 Tool Fallback Invented Facts**: How does the system handle tool fallback when a knowledge query tool is down? The agent must write a block report and list the missing questions instead of guessing or inventing decisions.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST define and enforce a tool routing matrix containing columns for `phase`, `task type`, `primary tool`, `specific skill/flow`, `input`, `output`, `validator`, and `stop condition`.
- **FR-002**: Every gate review file MUST contain a status header (`Status: PASS`, `Status: BLOCKED`, `Status: NEEDS_HUMAN_REVIEW`, or `Status: WARN`) and a `Blocking Issues:` key.
- **FR-003**: The gate MUST be considered blocked if the `Blocking Issues:` value is anything other than `none`.
- **FR-004**: The system MUST support a narrow feature identity pointer at `.ai/state/active-feature.json` that references only the canonical spec path `specs/<feature-slug>/`.
- **FR-005**: All mutable pipeline progress and validation status MUST live in `.ai/state/run-state.json`, including: `feature_slug`, `spec_path`, `current_phase`, `last_gate`, `last_gate_status`, `blocked_reason`, `retry_count`, `retry_scope`, and `verified_artifacts`.
- **FR-006**: The `verified_artifacts` field in the run state MUST be validator-owned and include path, artifact type, verifier name, timestamp, verification status, and optional content hash.
- **FR-007**: The system MUST implement a failure taxonomy with defined actions for: `Local Bug` (fix in-place), `Spec Drift` (return to spec phase), `Tool Unavailable` (graceful text-mode degradation logged to `.ai/state/block-report.md`), `Context Fragmentation` (read canonical references), `Path Drift` (block execution), and `Validation Loop Exhausted` (trigger human review).
- **FR-008**: Upon 3 consecutive validation failures for the same gate and scope, the system MUST transition the run state to `NEEDS_HUMAN_REVIEW` and generate a review packet at `.ai/reviews/<feature-slug>/human-review-packet.md` containing: `feature_slug`, `current_phase`, `gate`, `status: NEEDS_HUMAN_REVIEW`, `blocking_question`, `recommended_answer`, `options_considered`, `affected_artifacts`, and `resume_instructions`.
- **FR-009**: The Memory Handoff Gate (D-10) MUST enforce a hybrid gate requiring `.ai/state/handoff.md` to exist, reference the feature slug, list updated memory files, and link QA/session inputs before passing.
- **FR-010**: All seeded `.ai/memory/` files (project summary, decisions, architecture, risks, verification history) MUST be updated to contain actual Snail Agent Flow protocol facts.
- **FR-011**: The system MUST support resuming execution from a `NEEDS_HUMAN_REVIEW` state via a command-line resume/override flag (e.g., `--resume` or `--override-gate`) which resets the gate retry counters in `run-state.json`.

### Key Entities *(include if feature involves data)*

- **Active Feature Identity Pointer (`active-feature.json`)**: A static pointer indicating the active feature slug and its directory under `specs/`.
- **Run State (`run-state.json`)**: The central schema capturing pipeline progress, current phase, retry status, last gate reports, and validator-owned verified artifacts.
- **Gate Review Report**: A markdown document output by validators/gates containing a explicit `Status` header and `Blocking Issues` key.
- **Human Review Packet**: A structured schema/markdown file produced when human review is required, documenting the block, options, recommendations, and resume steps.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of pipeline phase transitions follow the specified tool routing matrix.
- **SC-002**: 100% of review gates output explicit statuses conforming to the gate status vocabulary (`PASS`, `BLOCKED`, `NEEDS_HUMAN_REVIEW`, `WARN`).
- **SC-003**: 100% of duplicate/drifted specification paths (e.g. outside `specs/<feature-slug>/`) are detected and blocked.
- **SC-004**: The system halts and writes a Human Review Packet within 1 execution step of the 3rd consecutive gate failure.
- **SC-005**: All seeded memory files under `.ai/memory/` contain zero placeholders and accurately reflect current repository architectural decisions.

## Assumptions

- The workspace continues to use Git for version control and branch management.
- The default format for structured data is JSON (for programmatically queried files like `run-state.json`) and Markdown (for human-readable gates/packets).
- Interactive tools (like prompt queries) may degrade to plain-text queries if run in non-interactive CI environments.
