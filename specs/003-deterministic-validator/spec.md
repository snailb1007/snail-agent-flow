# Feature Specification: Deterministic Validator, Drift Checks, and Human Review Packet

**Feature Branch**: `003-deterministic-validator`

**Created**: 2026-05-24

**Status**: Draft

**Input**: User description: "Deterministic Validator, Drift Checks, and Human Review Packet"

## Goal

To enforce structural specification rules, verify folder/heading layout completeness, check path correctness (prevent path drift), scan for placeholders, track validation retry/block states, and generate a human review packet after 3 consecutive validation failures without using non-deterministic LLM-as-judge calls.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Running the Deterministic Validator (Priority: P1)

As a developer or automation agent, I want to run a deterministic validator script so that I can immediately check if my feature specification, implementation plan, and task checklists are complete and conform to the project's formatting rules.

**Why this priority**: Core value of the MVP is to provide fast, 100% reproducible validation of specification documents without incurring API costs or non-deterministic outcomes.

**Independent Test**: Can be verified by running `node validators/scripts/validate-spec.js` against a feature spec folder and verifying the console logs the result and exits with code 0 on success, or code 1/10 with detailed error classifications on failure.

**Acceptance Scenarios**:

1. **Given** an active feature spec directory with all required files, headings, and no placeholders, **When** the validator runs, **Then** it updates `run-state.json` with status `PASS`, resets retry/failure counts, and exits with 0.
2. **Given** a spec directory missing `plan.md` or `tasks.md`, **When** the validator runs, **Then** it updates `run-state.json` with status `BLOCKED`, logs `Missing Required File` error, and exits with code 1.
3. **Given** a spec file containing forbidden placeholder text like `TODO` or `TBD`, **When** the validator runs, **Then** it updates `run-state.json` with status `BLOCKED`, logs `Open Clarification` error, and exits with code 1.

---

### User Story 2 - Path Drift & Spec-Kit Ownership Verification (Priority: P2)

As a workspace manager, I want the validator to verify that all feature specification artifacts live in the canonical feature directory and that no shadow/legacy spec folders are being used.

**Why this priority**: Prevents agent path drift and keeps the codebase cleanly organized. Enforces Spec-Kit ownership of the feature specifications stack.

**Independent Test**: Create a markdown file inside `.specify/specs/` or `specs/current/` and verify that the validator flags a `Path Drift` failure and blocks execution.

**Acceptance Scenarios**:

1. **Given** a markdown file exists under `.specify/specs/`, `specs/current/`, or `.ai/specs/`, **When** the validator runs, **Then** it flags a `Path Drift` violation and exits with code 1.
2. **Given** GSD attempts to run without a plan or checklist generated by Spec-Kit in the active feature directory, **When** the validator checks Spec-Kit ownership, **Then** it fails with `Missing Required File` or `Path Drift` and blocks.

---

### User Story 3 - Retry Tracking & Human Review Packet Generation (Priority: P3)

As a workflow operator, I want the validator to limit consecutive validation retries to 3, and upon reaching the limit, halt execution with a distinct exit code and write a structured human review packet.

**Why this priority**: Prevents infinite automated retry loops by routing the blocker context back to the human developer.

**Independent Test**: Run the validator 3 times consecutively on a failing spec directory, and check that on the 3rd run it updates status to `NEEDS_HUMAN_REVIEW`, writes `.ai/reviews/003-deterministic-validator/human-review.md`, and exits with code 10.

**Acceptance Scenarios**:

1. **Given** the validator runs and fails, **When** `consecutive_failures` is less than 3, **Then** it increments the counter, logs the error, and exits with code 1.
2. **Given** the validator runs and fails, **When** `consecutive_failures` becomes 3, **Then** it updates the status to `NEEDS_HUMAN_REVIEW`, writes the review packet at `.ai/reviews/<feature-slug>/human-review.md`, and exits with code 10.
3. **Given** a validation status of `NEEDS_HUMAN_REVIEW` or `BLOCKED`, **When** the operator fixes the files and runs the validator successfully, **Then** `consecutive_failures` is reset to 0, status is updated to `PASS`, and it exits with 0.

---

### Edge Cases

- **Mixed Placeholders**: If a spec file has multiple placeholders (e.g. `TODO` and `NEEDS CLARIFICATION`), the validator must catch all of them and report the locations in the output.
- **Nested Legacy Directories**: Legacy folders might have nested subdirectories. The path drift scan must run recursively to find any markdown file in those paths.
- **Malformed run-state.json**: If `run-state.json` is missing or is invalid JSON, the validator must fail with `Invalid JSON State` but still gracefully report the failure.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The validator MUST be a Node.js script located at `validators/scripts/validate-spec.js`.
- **FR-002**: The validator MUST resolve the active feature directory by reading the `feature_directory` key in `.specify/feature.json` or `.ai/state/active-feature.json`.
- **FR-003**: The validator MUST read and update `.ai/state/run-state.json` using the schema:
  - `feature_slug` (string)
  - `spec_path` (string)
  - `current_phase` (string)
  - `last_gate` (string)
  - `last_gate_status` (`PASS` | `BLOCKED` | `NEEDS_HUMAN_REVIEW`)
  - `consecutive_failures` (integer)
  - `last_failed_step` (string | null)
  - `last_failed_rule` (string | null)
  - `last_validator_output` (string | null)
  - `retry_count` (integer)
  - `retry_scope` (string)
  - `verified_artifacts` (array of objects)
  - `updated_at` (ISO timestamp)
- **FR-004**: The validator MUST recursively scan the following paths for any markdown files (`*.md`):
  - `.specify/specs/`
  - `specs/current/`
  - `.ai/specs/`
  If any match, it MUST fail with the classification `Path Drift`.
- **FR-005**: The validator MUST verify the existence of `spec.md`, `plan.md`, and `tasks.md` in the active feature directory. If any is missing, it MUST fail with `Missing Required File`.
- **FR-006**: The validator MUST verify that `spec.md` contains either an H1 heading (`# ...`) or an H2 `## Goal`, plus the exact H2 headings:
  - `## Non-Goals`
  - `## Acceptance Criteria`
  - `## Test Strategy`
  - `## Behavior-Preservation Rules`
  If any are missing, it MUST fail with `Missing Required Heading`.
- **FR-007**: The validator MUST verify that `plan.md` contains the exact H2 headings:
  - `## Proposed Changes`
  - `## Verification Plan`
  If any are missing, it MUST fail with `Missing Required Heading`.
- **FR-008**: The validator MUST verify that `tasks.md` contains a checklist of tasks (e.g. lines starting with `- [ ]` or `- [x]`). If no checklist matches, it MUST fail with `Missing Required Heading` or a similar checklist structure error.
- **FR-009**: The validator MUST search case-insensitively inside the active `spec.md`, `plan.md`, and `tasks.md` files for the following forbidden placeholder words:
  - `TODO`
  - `TBD`
  - `NEEDS CLARIFICATION`
  - `[NEEDS CLARIFICATION]`
  - `FIXME`
  - `XXX`
  If any are found, it MUST fail with `Open Clarification` and print the file name and line contents.
- **FR-010**: The validator MUST manage state and exit codes based on consecutive failures:
  - If validation passes: Set `consecutive_failures` to `0`, `last_gate_status` to `PASS`, update `run-state.json`, and exit with code `0`.
  - If validation fails and new `consecutive_failures` is `< 3`: Set `last_gate_status` to `BLOCKED`, update `run-state.json`, and exit with code `1`.
  - If validation fails and new `consecutive_failures` is `>= 3`: Set `last_gate_status` to `NEEDS_HUMAN_REVIEW`, generate a review packet at `.ai/reviews/<feature-slug>/human-review.md`, and exit with code `10`.
- **FR-011**: The human review packet generated at `.ai/reviews/<feature-slug>/human-review.md` MUST contain:
  - `feature_slug`
  - `current_phase`
  - `gate`
  - `status: NEEDS_HUMAN_REVIEW`
  - `blocking_question`
  - `recommended_answer`
  - `options_considered`
  - `affected_artifacts`
  - `resume_instructions`

### Key Entities

- **Active Feature Pointer**: Configured in `.specify/feature.json` or `.ai/state/active-feature.json`, pointing to the active feature path.
- **Run State (`run-state.json`)**: The state tracking file located at `.ai/state/run-state.json`.
- **Human Review Packet**: The markdown file created at `.ai/reviews/<feature-slug>/human-review.md`.

## Non-Goals

- Auto-fixing formatting or folder layout errors.
- Running external compilers, tests, or linters (this validator only verifies structural layout and spec quality).
- Integrating with visual dashboards or UI interfaces in this phase.

## Acceptance Criteria

- Running `node validators/scripts/validate-spec.js` executes in less than 200ms.
- 100% of missing files or missing headings in `spec.md`, `plan.md`, or `tasks.md` are caught.
- 100% of legacy spec paths containing markdown files trigger a `Path Drift` violation.
- The retry loop transitions to `NEEDS_HUMAN_REVIEW` and writes the review packet precisely on the 3rd consecutive failure.
- Resuming/passing validation correctly resets the retry counters to 0.

## Test Strategy

- **Unit/Integration Tests**: Write an automated test script (`validators/scripts/test-validator.sh` or a JS test runner) that mocks different spec folder configurations (missing files, missing headings, placeholders, path drift) and asserts the validator's output, exit codes, and `run-state.json` updates.
- **Simulation**: Run three consecutive simulated failures and verify that the human review packet is created correctly.

## Behavior-Preservation Rules

- The script MUST preserve existing fields in `run-state.json` that are not managed by the validator (e.g. `verified_artifacts` or other metadata fields).
- The script MUST NOT mutate any user feature files (`spec.md`, `plan.md`, `tasks.md`) under `specs/`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Execution time of the validator script is under 200ms for standard features.
- **SC-002**: 100% coverage of specified headings in `spec.md`, `plan.md`, and `tasks.md`.
- **SC-003**: 100% of forbidden placeholders are detected case-insensitively.
- **SC-004**: Exit codes are strictly 0 (success), 1 (blocked < 3 failures), and 10 (NEEDS_HUMAN_REVIEW on 3rd failure).

## Assumptions

- The workspace continues to use JSON for state tracking and Markdown for documentation and review packets.
- The Node.js runtime is installed in the execution environment.
